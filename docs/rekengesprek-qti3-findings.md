# Rekengesprek in QTI 3: findings

Rebuild of the "Rekengesprek" from the Leercheck Breuken demo
(cito-po-leercheck-demo-breuken-production.up.railway.app → Lesactiviteiten → Rekengesprek) as a QTI 3
assessment in this player, to find out what QTI 3 can express and what our player (`@citolab/qti-components`
9.3.0) still lacks.

## Current demos

Two small packages with the same mini-lesson. Both start with the same intro: the **rekendagboek** (`DAGBOEK`:
mood, confidence slider, cards) and pointing at the **teller / noemer** (`TELLER`, `NOEMER`: hotspots, unlimited
attempts). Then come the four steps of ½ + ¼ (gelijknamig maken, ½ omzetten, optellen, controleren). Each step has a
main question; wrong → "even dieper kijken" → retry → uitleg. Both are generated by
`tools/rekengesprek/generate.mjs` from the demo's own texts (`RG_STAPPEN`).

| | `public/rekengesprek` (tab *Adaptief: toets*) | `public/rekengesprek-adaptief` (tab *Adaptief: item*) |
| --- | --- | --- |
| Where the flow lives | the **test**: `qti-pre-condition` and `qti-branch-rule` on the item-refs | the **item**: `FASE` outcome in response processing |
| Items | 3 intro + 19 plain items (`S<n>_TUSSEN`, `_MAIN`, `_V1`, `_V2`, `_RETRY`), 1 attempt each | 3 intro + 4 `adaptive="true"` items (`S<n>_ADAPTIEF`), up to 3 attempts each |
| Tussenvragen | `S<n>_TUSSEN` only when the dagboek set `DAGBOEK.MODE = BEGELEID` (mood twijfel / spannend / zwaar) | not possible: response processing only sees the item's own variables, so it cannot read the dagboek |
| Right straight away | branch rule jumps to the next step's main question | `completionStatus = completed` after attempt 1 |
| Wrong | the next items in order: V1, V2, RETRY | attempt 2 shows the dieper-kijken questions (inside a `qti-feedback-block`), attempt 3 the retry |
| Reporting | every sub-question scored and reported on its own | one SCORE per step; sub-answers are only responses |
| Player support | needs qti-components PR #289 (branch rules) | renders in 9.3.0, but `done` / Controleer were wrong for adaptive items until PR #298 |

Both tests compute `DIRECT` (steps right straight away) the same way and show the same `qti-test-feedback`.

Missing player features were built here first and are now in qti-components (PR #289, #290, #298); the player runs on `@citolab/qti-components@10.0.0-next.2`.

## Findings from the full rebuild

The findings below come from an earlier, full rebuild of the demo (27 items: rekendagboek, teller/noemer
hotspots, own answer, "wat heb je gedaan?", tussenvragen with `qti-pre-condition`). That content was removed
to keep the comparison small; the findings still hold.

One `qti-test-part` (linear, individual) with one `qti-assessment-section`. Every question was an item; the
adaptivity lived in the **test**:

| Demo | QTI 3 |
| --- | --- |
| Rekendagboek: mood, confidence 1–5, cards | `DAGBOEK`: choice (`min-choices="1"`), `qti-slider-interaction`, choice `max-choices="0"`; `allow-skipping="false"` on the item-ref |
| Point at teller / noemer, "probeer het nog eens" | `TELLER`, `NOEMER`: `qti-hotspot-interaction` on an SVG of ½ + ¼; `max-attempts="0"` (unlimited) |
| Gelijknamig (multi-select), "mag je dit zo optellen?" | `GELIJKNAMIG` (2 correct values), `MAGZO` |
| "Zijn de stukjes even groot?" only after a wrong MAGZO | `STUKJES` with `qti-pre-condition`: `MAGZO.SCORE < 1` |
| Own answer, any fraction equal to ¾ is right, "Ik weet het niet" | `ANTWOORD`: 2 × `qti-text-entry-interaction`, `qti-equal(qti-product(T,4), qti-product(3,N))`, `qti-end-attempt-interaction count-attempt="true"`; outcomes `FEEDBACK` (EXACT / EQUIV / FOUT / WEETNIET) and `MODE` (ZELFSTANDIG / BEGELEID); the answer is echoed with `qti-printed-variable` |
| "Wat heb je gedaan?" only after a wrong answer | `WATDEED` with pre-condition `ANTWOORD.FEEDBACK = FOUT` |
| Tussenvraag only for a learner who needs guidance | `S<n>_TUSSEN` with pre-condition `ANTWOORD.MODE = BEGELEID` |
| Main question; right → next step, wrong → even dieper kijken → retry → uitleg | `S<n>_MAIN` with `qti-branch-rule` (`S<n>_MAIN.SCORE ≥ 1` → `S<n+1>_TUSSEN`, last step → `EXIT_TEST`); then `S<n>_V1`, `S<n>_V2`, `S<n>_RETRY` |
| Step 1 also accepts 8 ("8 kan ook…") | second accepted value with its own `FEEDBACK` (`GOED_ALT`) |
| One attempt per question, feedback stays | section default `max-attempts="1" show-feedback="true"` |
| Muurtje H / G / I | `category="muur-H stap-1"` on the item-refs |
| Steps solved straight away | test outcome processing `DIRECT = Σ S<n>_MAIN.SCORE` → `qti-test-feedback` |

## Validator notes (qti-azure `validate_qti_item`)

All item templates are XSD-valid. `QTI-SEM-002` ("response declaration not referenced by any interaction")
is a false positive for `qti-slider-interaction`, `qti-hotspot-interaction` and `qti-end-attempt-interaction`:
the validator does not count those as response references. The test XML (pre-conditions, branch rules) cannot
be checked with this tool; it is item-only.

## Does not fit QTI 3 (left out on purpose)

- **Monitor for the teacher** (every tap with a timestamp): that is logging / results reporting, not assessment
  content. The player keeps the item sessions; a log would be a host feature.
- **Overzicht** (strengths, development points, plan, child-friendly summary): outcome processing can compute
  the facts (e.g. `DIRECT`, per-step results, diary answers) and `qti-test-feedback` can show fixed texts per
  condition, but composing a personal analysis from diary, free text and steps is application logic. Skipped
  by decision for this version.
- **Show the "Anders…" text box only after choosing "Anders"**: a non-adaptive item cannot show interactions
  conditionally (only adaptive items may put interactions in feedback). WATDEED shows the text box always,
  marked optional.
- **One "Verder" button**: the demo checks and moves on with one click; QTI's individual submission gives
  *Controleer* (end attempt) and *Volgende* (navigate) as two steps.
- **Remembering the last finished gesprek** (localStorage in the demo): host concern; the player keeps the
  running session per package in `sessionStorage`.

## Test-level branching vs. adaptive item

- **Test-level branching** (main package): every question is a plain item that can be reused, scored and
  reported on its own; the flow is readable in `AssessmentTest.xml`. It needs pre-conditions and branch rules,
  which 9.3.0 lacks (in 10.0.0-next.2, PR #289).
- **Adaptive item** (`rekengesprek-adaptief`): works in 9.3.0 without extra code, but the whole step is one
  item with a hand-written state machine (`FASE` outcome), sub-questions are not separately reportable, and
  9.3.0 ended the item too early (`done`) and too late (Controleer after `completed`); fixed in PR #298.

## How it was verified

- `pnpm test:browser`: 11 tests pass (the existing Player test + 10 for pre-conditions, branch rules and
  boolean matching in `tests/next/`).
- Walked through in the dev server (driving the real controls), three paths:
  1. *Guided*: MAGZO wrong → STUKJES, answer 2/6 → WATDEED + every tussenvraag; step 1 all wrong (tussen,
     main, V1, retry) → reveal; step 2 main right → jump to step 3; step 3 via dieper kijken; step 4 main
     right → `EXIT_TEST` → results 12/20 with the "OP_WEG" feedback.
  2. *Independent*: MAGZO right (STUKJES skipped), answer 6/8 (EQUIV + printed 6/8), WATDEED and all
     tussenvragen skipped; step 1 "8" → GOED_ALT; branch targets with false pre-conditions skipped forward;
     results count only the 14 presented items.
  3. *"Ik weet het niet"*: WEETNIET feedback, WATDEED skipped, tussenvragen shown.
- Feedback texts match the demo's source 1:1 (generated from it).
- Visually checked: the TELLER hotspot item (boxes sit over the digits, selection highlighted), progress
  steps with skipped items, "Poging 1 van ∞". Not visually checked: the strip figures in the step items.
